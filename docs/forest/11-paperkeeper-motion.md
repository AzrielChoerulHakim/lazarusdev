# Stage 11 — Paperkeeper / quiet acting, never a mascot loop

**Scope:** A limited, user-initiated paper-character motion study across the five-chapter storybook. **Master:** locked Forest V2 + `05-character-bible.md`. Stage 12 transitions and other chapters are not redrawn.

## Visual acting rules implemented

Paperkeeper is the same asymmetric leaf-hatted, layered-moss-caped, twig-legged messenger with the satchel and acorn lantern. No newly invented character artwork, human explorer or glossy vector rig was introduced.

- **Entrance:** focusing or hovering the existing actual leaf navigation link yields one 450ms discrete hat-tip response, without delaying the link.
- **Winding Path:** a *field-note margin*, deliberately outside the forest illustration, displays the existing tiny Stage 05 `walk-a/b/c` drawings at their intended small scale. Clicking **Watch Paperkeeper take a step** triggers ten 100ms frame updates, then returns to stillness. No autoplay, repeat only by fresh click, never infinite. The large canonical Path Paperkeeper stays unchanged as scenery. This is *three unique drawings at 10 updates per second*, **not** a false claim of ten uniquely drawn full-resolution frames.
- **Work Clearing:** on hover or keyboard focus of the genuinely clickable hanging folio sheets, the existing Paperkeeper gives one small leaf-like glance, with the art links remaining fully usable.
- **River Stories:** the existing `paperkeeper.read.webp` small original pose appears in the journal's margin. Unfolding a native journal note produces one very small reading nod, still after 490ms.
- **House on the Hill:** each real user light-switch click may trigger one 450ms lantern acknowledgment; the window light interaction remains independent.

No rigging software, invented in-betweens, synthetic spritesheet, background music, sound playback or looped dancing. This is an intentionally restrained first *limited acting layer*, not a finished full-frame film. Visual composition remains tied to V2 and uses the original source colors and character silhouettes.

## Accessibility, user agency and failure behavior

Actual project navigation is unaffected, native page scroll is not intercepted, and no essential content relies on the character. The walking control is only enabled once all three authentic sprites are successfully preloaded. Its status is a semantic live region; repeated triggers are prevented during a one-second gesture. When the document is hidden, the tiny sequence is canceled. Changing the operating-system reduced-motion setting stops motion and hides the optional trigger; CSS acknowledgments are fully suppressed. With JavaScript off, the walking button is hidden and readable static content stays intact.

The figure in the walking study is decorative; the button provides the meaningful description, with no duplicated alt or fabricated story. Clicking the real House button doesn't submit a form or send contact info; Stage 10's honest local-only brief remains unchanged.

## Explicit future boundary

The Stage 05 action sprites are extremely small (64–84×95px) and are used only at a tiny native-adjacent scale. This stage **does not** upscale them into the large in-scene figure. Fully unique, high-resolution 8–12 drawing frames per second for long traversal would require separate commissioned art; this implementation does not misrepresent a three-drawing study as such. Multi-plane scene continuity and traversal controls are Stage 12; mobile-portrait redrawing is Stage 14.

## Proof requirements

A dedicated GitHub Action validates exact unchanged SHA-256 hashes against the Character Bible manifest; both HTML routes and scripts; build; browser behavior in eight viewports times two routes; all three real walking key swaps; absence of horizontal overflow and uncaught errors; visible actionable control >=44px; reduced-motion behavior and no-JavaScript fallback. Regression workflows for Stages 03 and 06–10 and GitHub Pages should pass on exactly the same promoted commit.

**No browser screenshots may be taken, stored or uploaded** by this stage. QA output is text logs only. Automated technical success must never be presented as mechanical proof of artistic perfection.
